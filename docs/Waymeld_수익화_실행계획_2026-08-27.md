# 「구독제 수익화」실행계획

> 목표: "구독제로 가고 싶다"는 방향을 실제로 결제가 도는 상태까지 만든다.
> 작성일: 2026-08-27
> 선행 문서: [Waymeld_수익화전략_검토보고서_2026-08-26.md](reports/Waymeld_수익화전략_검토보고서_2026-08-26.md) — 이 계획은 그 보고서 §4(권장 실행 순서)·§6(4가지 결정 사항 후속 조사)의 결론을 그대로 실행에 옮긴다.

---

## 0. 전제 — 이 계획이 다루는 범위

검토보고서에서 이미 확정된 것들은 재론하지 않고 전제로 깐다.

- **전략·UI·DB 스키마는 이미 있다.** `subscription.ts`(플랜 게이팅), `profiles` 테이블(`plan`/`subscription_status`/`subscription_expires_at`), `UpgradeModal.tsx`(업그레이드 UI) — 전부 5월에 완성됐다. 이번 계획이 새로 만드는 건 **결제 파이프라인 하나**뿐이다.
- **PG는 포트원(구 아임포트)을 경유해 토스페이먼츠 채널을 붙인다.** Stripe는 한국 사업자가 가입 자체를 못 하므로 스코프 밖(검토보고서 §6.1). 해외카드는 이번 계획에 포함하지 않는다.
- **가격은 더 고민하지 않고 확정한다.** **Plus 월 4,900원 / 연 29,000원(약 40% 할인)** 하나만 먼저 낸다. Team은 이번 계획 범위 밖 — 유료 전환자가 나온 뒤 별도로 설계(검토보고서 §4-6).
- **Free 플랜의 export 월 1회 무료는 이번 Tier 1에 넣지 않는다.** 결제 파이프라인과 동시에 바꾸면 무엇이 전환율에 영향을 줬는지 구분이 안 된다(검토보고서 §6.3). Tier 2 후반부, 베이스라인 관찰 이후로 미룬다.

## 1. 결제 아키텍처

### 1.1 전체 흐름

```
[사용자] --카드 등록(포트원 SDK)--> [프론트] --billingKey--> [Edge Function: billing-subscribe]
                                                                    |
                                                                    v
                                                        포트원 결제 API로 즉시 첫 결제
                                                                    |
                                                                    v
                                              profiles.plan='plus' / subscription_status='active'
                                              / subscription_expires_at = now + 1개월
                                              billing_customers, billing_events 기록

[포트원 웹훅] --결제성공/실패/취소--> [Edge Function: billing-webhook] --> profiles 갱신 (이중 안전장치)

[매일 크론] --만료 임박 구독 스캔--> [Edge Function: billing-charge] --> 저장된 billingKey로 재결제

[사용자] --해지 클릭--> [Edge Function: billing-cancel] --> subscription_status='cancelled'
                                                              (plan은 만료일까지 유지, 이후 크론이 free로 되돌림)
```

**중요한 설계 원칙**: 카드번호 자체는 우리 서버에 절대 저장하지 않는다 — 포트원이 발급한 `billingKey`(토큰)만 저장한다. `profiles.plan` 변경은 클라이언트에서 직접 쓰지 않고 **반드시 서비스 롤 키를 쓰는 Edge Function에서만** 이루어진다(지금 `profiles.ts`도 읽기 전용이며, RLS는 `select`/`update`를 `auth.uid() = id`로만 허용하므로 plan 컬럼을 사용자가 직접 조작할 수 없게 별도 컬럼 단위 정책이나 트리거로 막아둘 것 — 현재 정책은 행 전체 update를 허용하고 있어 이 부분은 Tier 1에서 함께 손봐야 한다).

### 1.2 DB 변경 (신규 마이그레이션)

기존 `profiles` 테이블은 그대로 재사용한다(`plan`, `subscription_status`, `subscription_expires_at`가 이미 있음). 새로 필요한 건 두 테이블뿐이다.

```sql
-- 빌링키 보관 (카드정보 자체는 저장하지 않음, 포트원 토큰만)
create table public.billing_customers (
  user_id uuid primary key references auth.users(id) on delete cascade,
  provider text not null default 'portone',
  billing_key text not null,
  card_last4 text,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

-- 결제 이벤트 로그 (웹훅 중복처리 방지 + 감사 추적)
create table public.billing_events (
  id uuid primary key default gen_random_uuid(),
  user_id uuid references auth.users(id) on delete set null,
  provider_event_id text unique,
  type text not null, -- 'payment_success' | 'payment_failed' | 'cancelled' | 'renewed'
  amount integer,
  raw_payload jsonb,
  created_at timestamptz not null default now()
);

alter table public.billing_customers enable row level security;
alter table public.billing_events enable row level security;
-- 두 테이블 모두 클라이언트 접근 정책을 만들지 않는다 (Edge Function의 서비스 롤 키만 접근)
```

기존 `profiles`의 update RLS 정책(`profiles_update_own`)은 지금 컬럼 제한 없이 행 전체 수정을 허용하고 있어, 사용자가 클라이언트에서 자기 `plan`을 `'plus'`로 직접 바꿔치기할 수 있는 구멍이다. Tier 1에서 컬럼 단위 정책(또는 트리거로 `plan`/`subscription_*` 변경을 서비스 롤에만 허용)으로 막아야 한다.

### 1.3 신규 Edge Functions (4개)

| 함수명 | 역할 |
|---|---|
| `billing-subscribe` | 프론트에서 발급받은 billingKey로 첫 결제 실행 + `billing_customers` 저장 + `profiles` 갱신 |
| `billing-charge` | 매일 크론이 호출 — 만료 임박(예: D-1) 구독을 찾아 저장된 billingKey로 재결제 |
| `billing-webhook` | 포트원 웹훅 수신 — 결제 성공/실패/취소를 `profiles`에 반영(비동기 이중 확인) |
| `billing-cancel` | 사용자의 "구독 해지" 요청 처리 — 즉시 결제 중단 표시, `plan`은 만료일까지 유지 |

`billing-charge`를 매일 돌릴 스케줄러는 Supabase의 `pg_cron`(사용 가능하면 가장 간단) 또는 외부 크론(GitHub Actions 스케줄 등, 이 저장소는 이미 `scripts/`에 빌드 스크립트가 있어 패턴은 익숙할 것)으로 Edge Function을 호출하는 방식 중 택1 — 현재 Supabase 프로젝트에서 `pg_cron` 확장 사용 가능 여부를 먼저 확인.

### 1.4 프론트 변경

- `UpgradeModal.tsx`의 `handleUpgrade`가 지금은 `window.location.assign(checkoutUrl)`로 외부 URL 이동을 가정하고 있는데, 포트원은 보통 **현재 페이지에서 SDK를 호출해 카드 등록 창을 띄우는 방식**이라 이 흐름을 교체해야 한다 — 외부 URL 리다이렉트가 아니라 모달 안에서 결제 SDK를 호출하는 구조로 변경.
- 결제 진행 상태 UI 추가: 로딩 → 성공(플랜 즉시 반영) → 실패(에러 메시지) 3단계.
- **구독 해지 버튼 신설**: 지금은 `getStripePortalUrl()`로 외부 포탈 이동만 상정돼 있는데, 공정위 가이드라인의 "간편한 해지" 요건(검토보고서 §6.4)을 확실히 충족하려면 앱 내부에 해지 버튼을 직접 두는 편이 안전하다. 마이페이지/설정 화면에 "구독 해지" 버튼 → `billing-cancel` 호출.

## 2. 법적 최소 요건 (결제 오픈과 동시에 필요)

- **이용약관·환불정책 페이지 신설.** 현재 저장소에 `/terms`, `/privacy` 등 약관 페이지가 전혀 없다 — 결제를 열기 전에 반드시 만들어야 한다. 공정거래위원회 정기결제 표준약관(ftc.go.kr 게시)을 뼈대로 서비스명·요금·환불 방식만 채워 넣는다(검토보고서 §6.4).
- 최소 포함 내용: ① 무료→유료 전환 고지(이번 설계에서는 카드 등록 즉시 결제이므로 "체험 후 자동전환" 시나리오 자체가 없어 해당 없음 — §6.3 참고) ② 해지 방법과 효력 발생 시점(이번 결제 주기까지 이용 가능) ③ 환불 규정(사용일수 비례 정산) ④ 환불수단 선택권.
- 결제 진입 전 약관 동의 체크박스 UI 추가.

## 3. 단계별 실행계획

### Tier 1 — 결제 파이프라인 (최우선, 약 1~2주 소요 전망)
- [ ] 포트원 가입 + 토스페이먼츠 채널 연동 신청 (PG 심사 대기 기간 있음 — 사업자등록 상태에 따라 수일~2주, 가장 먼저 착수해서 개발과 병행)
- [ ] DB 마이그레이션: `billing_customers`, `billing_events` 신설 + `profiles` update RLS 컬럼 단위로 제한
- [ ] Edge Function 4종 구현: `billing-subscribe`, `billing-charge`, `billing-webhook`, `billing-cancel`
- [ ] 크론 스케줄러 설정(`pg_cron` 또는 외부) — `billing-charge` 매일 실행
- [ ] `UpgradeModal.tsx` 결제 플로우를 외부 URL 리다이렉트 → 포트원 SDK 호출로 교체, 진행 상태 UI 추가
- [ ] 마이페이지에 "구독 해지" 버튼 + `billing-cancel` 연동
- [ ] 이용약관·환불정책 페이지 신설(공정위 표준약관 기반) + 결제 전 동의 체크박스
- [ ] 포트원 테스트 모드로 전체 플로우 리허설: 카드 등록 → 첫 결제 → `profiles.plan` 반영 확인 → 해지 → 만료 후 free 복귀 확인

### Tier 2 — 비용 방어 + 후속 기능 (Tier 1 완료 후 2~3일)
- [ ] `canRunGoogleSearch`/`recordGoogleSearch`를 `localStorage` → 서버(Supabase) 집계로 이관 (직전 구글맵 검토보고서 권고)
- [ ] Plus/Team에도 서버 측 소프트캡(일 300회 제안) 적용 — "무제한" 문구는 유지, 남용만 차단(검토보고서 §6.2)
- [ ] 결제 오픈 후 **2~4주 베이스라인 전환율 관찰**
- [ ] 베이스라인 확보 후 Free 플랜에 export 월 1회 상시 제공 추가(`canExportItinerary` 조건 확장) — 자동전환형이 아니므로 별도 고지 절차 불필요(검토보고서 §6.3)

### Tier 3 — 확장 (유료 전환자 발생 후 별도 착수)
- [ ] Team/B2B 플랜 설계 (5월 문서 §4 아이디어 순서대로 검토)
- [ ] 해외카드 결제(포트원 + 페이레터 등) 도입 여부 — 실제 수요(고객 문의, 결제 실패 로그) 확인 후 판단
- [ ] 가격 정밀화(A/B 등) — 지금은 가설 검증 단계이므로 보류

## 4. 리스크

- **PG 심사 대기 기간이 병목이 될 수 있다.** 개발 자체는 며칠이면 되지만 포트원/토스페이먼츠 심사가 늦어지면 전체 일정이 늘어난다 — 가장 먼저 신청부터 넣을 것.
- **웹훅 실패에 대비한 이중화.** `billing-subscribe`(즉시 처리)와 `billing-webhook`(비동기 확인)을 모두 두는 이유가 이거다 — 한쪽이 실패해도 다른 쪽이 상태를 보정할 수 있어야 한다. `billing_events.provider_event_id`에 유니크 제약을 걸어 웹훅 중복 처리(같은 이벤트 두 번 반영)를 막을 것.
- **크론 재결제 실패 처리.** 카드 만료·잔액 부족 등으로 재결제가 실패하면 즉시 `plan`을 내리지 말고 최소 1~2회 재시도 유예(예: 3일) 후 다운그레이드하는 편이 이탈을 줄인다 — 이번 계획에서는 최초 버전은 단순하게(1회 실패 시 즉시 알림 + 유예 없이 만료 처리)로 시작하고, 실제 실패율을 본 뒤 유예 로직을 추가해도 늦지 않다.

---

## 5. 결정이 필요한 사항

- **크론 방식** — `pg_cron`(Supabase 확장) 사용 가능 여부를 프로젝트에서 먼저 확인 필요. 안 되면 외부 스케줄러(GitHub Actions 등)로 대체.
- **연 요금제를 Tier 1에 같이 낼지, 월간만 먼저 낼지** — 복잡도를 줄이려면 월간 하나만 먼저 열고 연 요금제는 Tier 2 이후로 미루는 것도 방법. 최종 판단 필요.
