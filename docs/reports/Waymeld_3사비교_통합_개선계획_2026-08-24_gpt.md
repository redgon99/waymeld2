## 0. 결론 먼저

세 문서 모두 독립적으로 도달한 결론이 같다 — **Waymeld의 자리는 "장소를 찾는 서비스"가 아니라 "찾은 장소를 실제 이동시간·제약조건까지 반영해 실행 가능한 다일차 일정으로 바꾸는 엔진"**이라는 것. 이건 이미 오늘 앞서 두 차례(통합 개발계획 검토, canvas 기반 통합안) 확인한 결론과도 일치한다.

이번 GPT 3편은 앞선 canvas 두 개보다 훨씬 구체적이라 실제로 새로 챙길 것이 몇 개 나왔다. 코드베이스를 대조 검증한 결과:

- **이미 있는데 활용을 안 하고 있는 자산 하나를 발견했다** — Reddit/YouTube/네이버 블로그를 수집·분석하는 `insight-collect-*`/`insight-analyze` 파이프라인이 이미 라이브인데, 지금은 관리자 시장조사·범용 여행팁 가이드로만 쓰이고 **개별 장소에는 전혀 연결돼 있지 않다.** KTG 분석이 제안한 "Social Travel Intelligence"(장소 카드에 Reddit 반응 표시)는 사실 새로 만드는 게 아니라 이미 있는 파이프라인의 출력을 장소 단위로 연결만 하면 되는 일이다.
- **진짜로 없는 것도 확인했다** — OG 태그·사이트맵이 전혀 없어(마이리얼트립 분석이 지적한 "유입 부족"이 사실로 확인됨), 공유 링크가 카카오톡·SNS에서 미리보기 없이 뜬다. `supabase.channel`/Realtime 구독 코드는 프런트엔드 어디에도 없어(Wayby 분석이 강조한 실시간 공동편집은 코드 기준 완전히 0에서 시작하는 항목이다), 우선순위를 신중히 매겨야 한다.
- **KTG 분석의 "AI가 완전 자동으로 일정을 생성하고 가중치로 장소를 재점수화"하는 방향은 오늘 오전 검토했던 「통합 개선 개발계획」의 VRPTW 엔진 과대설계 위험과 같은 패턴이다.** 지금 Waymeld는 사용자가 직접 핀업하고 결정론적 최적화기가 순서를 잡는 구조이며, AI는 시나리오 카탈로그 서술에만 관여한다. 이 구조를 전면 교체하자는 제안은 그대로 받지 않는다.

## 2. 코드베이스 대조 검증 — "제안"과 "현실"을 나눔

세 문서 모두 GPT가 외부에서 관찰 가능한 정보(공식 사이트·앱스토어·약관, 그리고 `redgon99/waymeld` 저장소 훑어보기)로 작성했다. 실제로 코드를 열어 확인한 결과는 다음과 같다.

### 2.1 예상보다 이미 갖춰진 것

| 문서가 "필요하다"고 한 것 | 실제 코드 상태 | 의미 |
|---|---|---|
| KTG 문서 P1-08 "Reddit 여행정보 AI 분석"(#8), 최종 3대 차별화 중 "Social Travel Intelligence" | `insight-collect-reddit`/`insight-collect-youtube`/`insight-collect-naver` + `insight-analyze`(Claude로 pain_point/feature_request/praise/useful_tip 분류) + `insight_raw_items`/`insight_analysis` 테이블이 이미 라이브. 다만 **장소(content_id)와 연결되는 컬럼이 없고**, 현재는 관리자 시장조사 대시보드(`AdminInsightsPage`)와 범용 "여행팁 가이드 아티클"(`useful_tip_guides`, `GuidesPage`)로만 소비됨 | 신규 파이프라인 구축이 아니라 **기존 파이프라인에 `place_content_id` 컬럼 하나 추가 + 장소 카드에 요약 배지 노출**로 상당 부분 흡수 가능 — 비용이 문서가 암시하는 것보다 훨씬 낮음 |
| Wayby 문서 P0 "여행 수집함"(SNS/블로그 공유 → 자동 장소후보 저장) | `link-places-extract`, `youtube-places-extract` Edge Function이 이미 존재(URL에서 장소 추출) | 이미 상당 부분 구현됨. Wayby의 Clip Box와 실질적으로 같은 기능이 이미 있다는 뜻 — 격차는 "모바일 공유시트에서 몇 번 탭으로 저장되는가"라는 진입 마찰 쪽에 더 가깝다 |

### 2.2 문서 지적이 실제로 맞는 것(진짜 갭)

| 문서 지적 | 검증 결과 |
|---|---|
| 마이리얼트립 문서: "SPA 폴백, 고정 메타, 사이트맵·페이지별 OG 부재로 검색 유입이 약하다" | **사실로 확인.** `index.html`에 `og:title`/`og:image`/`og:description` 태그가 전혀 없고, `public/`에 `sitemap.xml`/`robots.txt`가 없음. 공유 링크(카카오톡/트위터 등)에 미리보기가 안 뜨는 상태 |
| Wayby 문서: 실시간 공동편집이 Waymeld에 "가장 우선적으로 따라잡아야 할" 항목 | 프런트엔드 어디에도 `supabase.channel`/Realtime 구독 코드가 없음(`grep` 결과 0건). **완전히 0에서 시작하는 항목**이라는 뜻 — 권한모델·충돌해결·활동로그까지 포함하면 가볍지 않다 |
| Wayby/KTG 공통: "순서 고정"과 별개로 "시간(도착시각) 고정"이 필요 | `Place`에 `priority?: number`(필수 핀 개념)는 있지만 명시적인 "도착시각 고정" 불린/필드는 없음. 지적이 정확함 |

### 2.3 문서 제안 중 그대로 받지 않는 것

**KTG 문서의 "AI Itinerary Engine"**(사용자 조건+POI+영업시간+날씨+이동시간+평가를 AI에 넣어 완전 자동으로 최적 일정을 뽑는 구조)와 **가중치 점수화 알고리즘**(취향25%+이동거리20%+날씨15%+...)은, 오늘 오전 「통합 개선 개발계획」검토에서 지적했던 것과 같은 함정이다 — 실제 데이터(영업시간·좌표 등)가 지저분해서 이론상의 가중치 최적화가 실전에서 튜닝 없이 바로 동작하지 않는다. 게다가 지금 Waymeld는 **사용자가 직접 장소를 고르고 결정론적 최적화기가 순서를 잡는 구조**이기 때문에, 이걸 "AI가 알아서 다 짜주는" 구조로 바꾸는 건 기존 UX 철학(사용자가 계획의 주인)과도 어긋난다.

**받아들이는 부분만 추린다**: 점수화 요소 목록(취향·이동거리·날씨·혼잡도·운영시간)은 **AI가 완전 자동 생성**하는 데 쓰지 않고, 이미 있는 결정론적 최적화 결과 위에 **"이 장소를 왜 넣었는지" 설명 문구**나 **후보 우선순위 제안** 정도의 보조 신호로만 흡수한다(이는 오늘 앞서 작성한 canvas 기반 통합계획의 T1-06과 같은 방향).

## 3. 세 문서가 서로 다르게 말하는 지점 — 내 판단

### 3.1 실시간 공동편집의 우선순위

- Wayby 문서: P0("가장 우선적으로 따라잡아야 할 기능")
- 오늘 앞선 두 리포트(통합 개발계획 검토, canvas 기반 통합계획): P2/T3(신중 검토, 뒤로 미룸)

**내 판단**: 우선순위를 유지한다. 이유는 두 가지다. 첫째, 2.2에서 확인했듯 Realtime 관련 코드가 전혀 없어 권한모델·충돌해결·활동로그까지 포함하면 독립 프로젝트급이다. 둘째, Wayby 자신도 사용 사례가 "데이트·친구 약속·당일 여행"에 쏠려 있다고 문서가 밝히고 있다 — 실시간성이 가장 중요한 시나리오는 "지금 같이 짜는 하루"이지, Waymeld의 핵심 시나리오인 "며칠짜리 여행을 미리 짜는 것"에서는 비동기 공유(공유마당)로도 상당 부분 대체된다. 다만 완전히 무시하지는 않는다 — **1단계로 "누가 지금 이 일정을 보고 있는지"(presence, 조회자 표시)만 가벼운 Realtime 구독으로 먼저 넣고**, 진짜 동시편집(락 없는 갱신, 충돌 해결)은 그 반응을 보고 결정한다.

### 3.2 마이리얼트립 연동 방식은 세 문서 중 가장 구체적이고 안전하다

마이리얼트립 문서가 제안한 **"일정 객체 분리"**(자유장소=자유최적화 / 예약형체험=시작시간·소요시간 고정 / 숙소=하루의 출발·종료 앵커 / 항공=전체 여행의 경계)는 오늘 앞서 canvas 기반 리포트에서 내가 제안한 "note 필드에 URL만 붙이기"(T1-04)보다 한 단계 더 발전된 아이디어다. 다만 문서가 제안한 순서(투어·티켓부터, 결제는 안 하고 클릭·전환만 추적) 자체가 이미 신중해서 그대로 받아들인다 — 첫 연동에서 마이리얼트립 마케팅파트너 가입·API 키 발급이 필요한데, 이건 사업자 심사가 걸려 있어 시간이 걸릴 수 있으므로 **API 연동 전에 먼저 사용자가 직접 붙여넣는 URL 버전(Tier 1)으로 수요 신호부터 확인**하고, 실제 클릭이 쌓이면 공식 제휴로 넘어가는 게 맞다.

## 4. 실행 우선순위 (통합)

## 6. 결론

이번 GPT 3편은 앞선 두 차례 리포트(오전 「통합 개선 개발계획」검토, canvas 기반 통합계획)보다 구체적이어서 실제로 반영할 것이 늘었다 — 특히 **SEO 배관(OG·사이트맵)이 진짜로 비어 있다는 것**과 **Reddit/YouTube 인사이트 파이프라인이 이미 있는데 장소 단위로는 연결이 안 돼 있다는 것**은 이번에 코드를 직접 대조해서 새로 확인한 사실이다. 반대로 KTG 문서의 "AI 완전 자동 일정 생성" 방향과 Wayby 문서의 "실시간 공동편집 최우선" 제안은 실제 코드 상태(결정론적 최적화기 중심 구조, Realtime 코드 0건)에 비춰 각각 부분 수용·신중 검토로 조정했다. Tier 1 항목 5개는 신규 스키마 없이 2~3주 내 착수 가능하며, 그중 T1-01(SEO)과 T1-02(인사이트-장소 연결)가 이번 분석에서 새로 발견된 가장 비용 대비 효과가 큰 항목이다.
