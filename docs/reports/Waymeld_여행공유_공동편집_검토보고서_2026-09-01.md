# 여행 공유 · 공동편집 기능 검토보고서

작성일: 2026-09-01

## 0. 결론 요약

**이 기능은 처음부터 설계할 필요가 없습니다.** `2026-08-11`에 이미 `trip_collaborators`
테이블과 owner/editor/viewer RLS 정책이 DB에 만들어졌는데, 프론트엔드 코드 어디에서도
쓰이지 않는 죽은 인프라로 남아 있었습니다(`grep` 결과 참조 실 0건). 즉 이번 작업은
"신규 기능 설계"가 아니라 **"이미 절반 만들어진 기능을 완성하고, 그 과정에서 발견된
버그 2개를 고치는 것"**에 가깝습니다.

또한 `PlanId`가 `'free' | 'plus' | 'team'`으로 이미 정의돼 있는데, `team` 플랜은 현재
`plus`와 완전히 동일하게 동작합니다(`isPlusOrTeam()`으로 항상 묶여서 처리됨) — **공동편집이
바로 이 "Team" 플랜을 실체화할 기능**이라는 뜻입니다. 수익화 관점에서도 자리가 이미
비어 있습니다.

권장안은 아래 "4. 권장 아키텍처"이며, 사용자가 제시한 옵션 1·2를 모두 포함하면서
실시간 동시편집(Google Docs류) 없이도 실용적으로 동작하는 **"공유 링크 + 협업자 관리
+ 낙관적 잠금"** 방식입니다.

## 1. 기존 인프라 조사 결과

### 1-1. 이미 존재하는 것 (죽어있는 인프라)

`supabase/migrations/20260811000000_trip_collaborators.sql`:

```sql
create table public.trip_collaborators (
  trip_id    uuid not null references waymeld_trips(id) on delete cascade,
  user_id    uuid not null references auth.users(id) on delete cascade,
  role       text not null default 'editor',  -- 'editor' | 'viewer'
  invited_by uuid references auth.users(id) on delete set null,
  created_at timestamptz not null default now(),
  primary key (trip_id, user_id)
);
```

`20260812000000_fix_trips_rls_recursion.sql`에서 `is_trip_collaborator()` /
`is_trip_owner()` SECURITY DEFINER 헬퍼로 순환참조를 끊고, `waymeld_trips`의
select/update RLS에 협업자 조건을 이미 추가해 두었습니다.

**프론트엔드 사용처: 0건.** `src/`, `supabase/functions/` 어디에도
`trip_collaborators`를 참조하는 코드가 없습니다. UI도, API도, 초대 로직도 없습니다.

### 1-2. 조사 중 발견한 버그 2개 (구현 전 반드시 고쳐야 함)

**버그 A — RLS가 editor/viewer를 구분하지 않음.**
`owner_update` 정책은 `is_trip_collaborator(id)`만 확인하는데, 이 함수는 role과
무관하게 `trip_collaborators`에 행이 있으면 무조건 `true`를 반환합니다. 즉 지금
스키마 그대로 쓰면 **'viewer' 권한으로 초대된 사람도 DB update가 그냥 통과됩니다.**
사용자가 요청한 "보기만" 옵션이 RLS 레벨에서는 전혀 강제되지 않는 상태입니다.

**버그 B — 저장 로직이 "현재 로그인한 사람 = 소유자"를 가정.** `PlannerPage.tsx`의
저장 경로(`handleShareConfirm`, 자동저장 effect 등) 여러 곳에서
`tripsRepo.save({ ...trip, ownerId: userId ?? undefined })` 패턴을 씁니다. 여기서
`userId`는 **지금 로그인한 사용자**입니다. 협업자(소유자가 아닌 사람)가 공유받은
여행을 열어서 저장하면, 이 코드가 `owner_id`를 협업자 자신의 id로 덮어써서
**소유권이 그대로 탈취됩니다.** 공동편집을 켜기 전에 이 패턴부터 "owner_id는 절대
덮어쓰지 않는다"로 고쳐야 합니다.

**버그 C(경미) — 조회 쿼리가 협업자를 아예 안 봄.** `src/lib/trips.ts`의
`listRemote`/`readRemoteLatest`/`readRemoteById`/`migrateLocalToUser` 전부
`.eq('owner_id', userId)`로 하드코딩돼 있어서, RLS가 허용해도 애초에 "내 여행"
목록에 공유받은 여행이 뜨지 않습니다.

### 1-3. 기존 "공유" 기능과의 관계 (겹치지 않게 설계해야 함)

현재 있는 공유는 **완전히 다른 메커니즘**입니다:

- `ShareTripModal` → `is_public=true` + `slug` 설정 → `/trip/:slug`
  (`ShareTripPage`, 로그인 불필요 익명 읽기 전용) 링크 생성 + 클립보드 복사/OS 공유시트
- 별도로 "공유마당" 체크박스를 켜면 공개 디렉토리에도 등재(이건 이메일은 연락처
  용도일 뿐, 초대 대상이 아님)

즉 지금도 "링크로 보기 공유"는 이미 있습니다. 이번에 새로 만들 것은 **"특정 사람에게
편집 권한을 부여하는" 부분**입니다. 두 기능은 공존해야 합니다(불특정 다수에게
보여주는 링크 vs 특정 인원에게 편집권 부여).

### 1-4. 이메일 발송 인프라: 없음

`supabase/functions/`를 전부 확인했지만 이메일 발송 함수가 없습니다. 현재 유일한
이메일 관련 기능은 Supabase Auth의 매직링크 로그인(`signInWithOtp`)뿐이고, 이건
Supabase가 자체 발송하는 로그인 메일이라 임의 초대 문구를 못 담습니다. **"이메일로
공유" 옵션을 진짜로 구현하려면 이메일 발송 채널을 하나 추가해야 합니다** (아래
4-3 참조).

## 2. 사용자가 제시한 옵션 검토

### 옵션 1 — 이메일로 공유(보기 전용 / 편집 가능 두 옵션)

기술적으로 타당하지만, "이메일 발송" 자체가 없는 상태에서 시작해야 합니다. 또한
이메일 주소만으로 권한을 부여하면 **그 이메일로 아직 가입 안 한 사람**을 어떻게
처리할지 정해야 합니다 → 옵션 2와 자연스럽게 연결됩니다.

### 옵션 2 — 공유받은 사람은 보기만, 회원가입하면 편집 가능

이건 사실 "초대 승낙 = 회원가입"을 강제하는 모델인데, 두 가지 하위 케이스가
갈립니다:

- **(a) 이메일 특정 없이 링크만 공유** → 링크를 연 사람은 누구나 "보기"고,
  로그인하면 자동으로 "편집자"가 됨 → **위험합니다.** 링크가 유출되면 누구든
  로그인만 하면 내 여행을 고칠 수 있게 됩니다.
- **(b) 이메일을 지정해서 공유** → 그 이메일로 가입/로그인한 사람만 편집자가 됨
  → 안전하고, 옵션 1과 자연스럽게 합쳐집니다.

**따라서 "이메일 없이 링크만으로 편집권을 주는 방식은 채택하지 않는 것을
권합니다.** 편집권은 항상 이메일로 특정된 사람에게만 부여해야 합니다.

### (제가 제안하는) 옵션 3 — 소유자가 앱 안에서 협업자를 직접 관리

지금 있는 `/trip/:slug` 공개 링크는 그대로 "보기 전용 공유"로 계속 쓰고, 그
위에 **"협업자 관리" 패널을 하나 추가**합니다:

1. 소유자가 여행 상세에서 "이메일로 편집 초대" 입력 → `trip_collaborators`에
   `role='editor'` 행 생성(아직 가입 안 했으면 `user_id`는 초대장 처리로 나중에
   연결 — 4-2 참조)
2. 초대받은 사람이 해당 이메일로 로그인하면, 그 여행이 자동으로 "내 여행" 목록에
   나타남(플래너 안에서 편집 가능)
3. 소유자는 "협업자 관리"에서 언제든 role을 editor↔viewer로 바꾸거나 제거 가능

이 방식은 옵션 1+2를 합친 것이면서, "링크 하나로 전체 편집권 유출" 리스크가 없고
(협업자는 이메일 단위로 개별 관리됨), 기존 공유 기능과 충돌하지 않습니다. **아래
권장 아키텍처는 이 옵션 3을 기본으로 합니다.**

## 3. 동시편집 방식: 실시간(CRDT) vs 낙관적 잠금

| | 실시간 동시편집 (Google Docs식) | 낙관적 저장 (권장) |
|---|---|---|
| 구현 난이도 | 매우 높음 — CRDT/OT, WebSocket presence, 커서 동기화 | 낮음 — `updated_at` 비교만 추가 |
| 인프라 | Supabase Realtime 채널 상시 유지, 별도 상태관리 필요 | 기존 저장 흐름 그대로 |
| 여행 계획 도구에 필요한가 | 과함 — 핀 목록/일차별 배치는 문서 편집처럼 글자 단위 충돌이 안 남 | 충분 — "같은 시각에 둘이 동시 저장"은 실제로 드묾 |
| 충돌 시 사용자 경험 | 자동 병합(구현 복잡, 버그 시 데이터 손상 위험) | "다른 사람이 방금 수정했어요, 새로고침할까요?" 안내 후 재시도 |

**권장: 낙관적 저장.** 여행 동선 데이터는 텍스트 문서가 아니라 구조화된
JSON(`payload`)이라 문자 단위 실시간 병합의 이득이 크지 않습니다. `waymeld_trips`에
`updated_at`이 이미 있으니, 저장 직전에 서버의 `updated_at`을 한 번 더 확인해서
내가 불러온 시점보다 최신이면 "덮어쓸까요?" 확인만 추가하면 충돌의 90%는
방지됩니다. 실시간 프레즌스("지금 OO님이 보고 있어요")는 Tier 3(선택)으로 미룹니다.

## 4. 권장 아키텍처

### 4-1. RLS/스키마 수정 (버그 A 수정 — 최우선)

```sql
-- owner_update 정책에서 role='editor'인 협업자만 통과하도록 헬퍼 분리
create or replace function public.is_trip_editor(p_trip_id uuid)
returns boolean language sql stable security definer set search_path = public as $$
  select exists (
    select 1 from public.trip_collaborators tc
    where tc.trip_id = p_trip_id and tc.user_id = auth.uid() and tc.role = 'editor'
  );
$$;

drop policy if exists "owner_update" on public.waymeld_trips;
create policy "owner_update" on public.waymeld_trips
  for update
  using (auth.uid() = owner_id or public.is_trip_editor(id))
  with check (auth.uid() = owner_id or public.is_trip_editor(id));
-- select 정책은 is_trip_collaborator(viewer 포함) 유지 — 보기는 editor/viewer 둘 다 허용
```

### 4-2. 초대 플로우 (아직 가입 안 한 사람 처리)

`trip_collaborators.user_id`는 `auth.users` FK라서 가입 전엔 행을 만들 수 없습니다.
그래서 **보류 초대 테이블**을 하나 추가합니다:

```sql
create table public.trip_invites (
  id         uuid primary key default gen_random_uuid(),
  trip_id    uuid not null references waymeld_trips(id) on delete cascade,
  email      text not null,
  role       text not null default 'editor' check (role in ('editor','viewer')),
  invited_by uuid not null references auth.users(id),
  created_at timestamptz not null default now(),
  accepted_at timestamptz
);
```

가입/로그인 시(AuthContext의 `syncLocalTrips`와 같은 자리) `auth.users.email`로
`trip_invites`를 조회해서, 일치하는 행이 있으면 `trip_collaborators`에 옮기고
`accepted_at`을 채우는 Edge Function 하나(`accept-trip-invites`)를 추가하면 됩니다.
이미 가입돼 있는 이메일이면 초대 즉시 `trip_collaborators`에 바로 꽂아도 됩니다.

### 4-3. 이메일 발송

두 단계로 나눠서 리스크를 낮추는 걸 권합니다.

- **Tier 1 (이메일 발송 없이 시작)**: 초대 시 이메일 발송 없이 "초대 링크"만
  생성해서 소유자가 카카오톡/문자 등으로 직접 전달(지금 있는 `navigator.share`
  재사용). 링크에 초대 토큰을 담아 클릭 시 로그인 후 자동으로 collaborator
  연결. **이메일 발송 서비스 없이도 옵션 1·2 요구사항을 대부분 충족합니다.**
- **Tier 2 (실제 이메일 발송)**: Resend(무료 티어 존재, Supabase 커뮤니티에서
  가장 흔히 씀) 등을 붙여 Edge Function에서 초대 메일을 직접 발송. 이때부터
  "이메일 주소만 입력하면 상대방 메일함에 초대장이 도착"이 됩니다.

Tier 1만으로도 "이메일 기반 권한 관리"(누구 이메일에 어떤 role인지 DB에 정확히
기록)는 완성되고, 실제 메일 발송(Tier 2)은 UX 개선 사항으로 나중에 붙여도
무방합니다.

### 4-4. 프론트엔드 변경 범위

- `src/lib/trips.ts`: `listRemote`/`readRemoteLatest`/`readRemoteById`에
  `trip_collaborators` JOIN 또는 별도 쿼리로 협업 여행도 포함하도록 수정
  (버그 C 수정)
- 저장 경로 전반: `ownerId`를 현재 로그인 사용자로 덮어쓰는 패턴 제거 —
  기존 `trip.ownerId`를 그대로 유지하도록 수정(버그 B 수정) — **공동편집
  여부와 무관하게 지금 당장 고쳐도 되는 잠재 버그**
- 새 컴포넌트: `CollaboratorsModal`(협업자 목록 + 이메일 초대 입력 + role 변경/제거)
- `PlannerAppBar`/`PlannerPage`: "협업자 관리" 진입점 추가(공유 버튼 옆),
  뷰어로 열었을 때 편집 UI 비활성화(읽기 전용 배너)
- `useAuth`/로그인 콜백 부근: 로그인 성공 시 `trip_invites` 수락 처리 호출

### 4-5. 플랜 게이팅

`team` 플랜이 이미 있으니, 공동편집(협업자 초대)을 `plan === 'team'` 전용으로
게이팅하는 게 자연스럽습니다. Free/Plus는 "보기 전용 링크 공유"까지만, 실제
편집권 초대는 Team부터. (가격/전환 전략은 별도 논의 필요 — 이 보고서 범위 밖)

## 5. 단계별 실행 계획

| 단계 | 내용 | 선행 이메일 인프라 필요 |
|---|---|---|
| Tier 1 | 버그 A·B·C 수정 + `trip_invites` 테이블 + 초대 링크(발송 없이 공유) + 협업자 관리 UI + 낙관적 저장 충돌 안내 | 불필요 |
| Tier 2 | Resend 등으로 실제 초대 메일 발송 | 필요 |
| Tier 3 (선택) | Supabase Realtime으로 "지금 보고 있는 사람" 표시(프레즌스만, 실시간 병합은 X) | 불필요 |

Tier 1만으로 사용자가 요청한 "이메일 특정 + 보기/편집 두 옵션 + 가입해야 편집
가능"이 전부 동작합니다. 다만 초대 전달은 소유자가 직접 링크를 보내야 합니다
(문자/카톡). Tier 2에서 "우리가 대신 메일을 보내드립니다"가 추가됩니다.

## 6. 리스크 정리

- **소유권 이전 없음**: 이 설계는 "협업자 추가/제거"만 다루고 owner 자체를
  바꾸는 기능(소유권 양도)은 포함하지 않습니다. 필요하면 별도 검토.
- **삭제 권한**: 여행 삭제(`owner_delete`)는 지금처럼 소유자만 가능하게 유지
  권장(editor도 삭제까지 허용하면 사고 위험 큼).
