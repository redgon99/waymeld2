## 1. 세 분석이 공통으로 가리키는 자리

| | Wayby | 마이리얼트립 | KoreaTravel Guru |
|---|---|---|---|
| 파는 것 | 하루 동선의 **순서** | 여행 **상품**(재고·결제·CS) | **어디가 갈 만한가**의 판단 |
| 단위 | 하루 | 상품 1건 | 장소 1개 |
| 신뢰 원천 | 원터치 최적화의 단순함 | 결제·후기·CS 인프라 | 출처·검수·현지 팁 |
| 여로담과의 겹침 | 큼(검색·지도·최적화) | 작음(동선 vs 거래) | 중간(정보 vs 실행) |

세 분석 모두 결이 다르지만 결론은 한 방향을 가리킨다 — **여로담이 실제로 차지하고 있는(또는 차지해야 하는) 자리는 "여러 곳에서 고른 장소를, 며칠짜리 몇 시 시간표로 만들고 현장에서 쓰는 것"이며, 이건 세 경쟁자 중 누구도 정면으로 하지 않는 일**이다. Wayby는 하루·같이 짜기에 강하고, 마이리얼트립은 상품 거래에 강하고, KTG는 장소 판단에 강하다. 다일차 시간표는 셋 다 비어 있다.

이 결론은 이미 검토했던 「통합 개선 개발계획」의 핵심 결론(§0)과 방향은 같지만, 그 문서는 이걸 실행하기 위해 VRPTW급 신규 엔진과 15개 신규 테이블을 요구했다. 아래 개선계획은 같은 결론에서 출발하되 **지금 있는 코드(`scenario_catalog`, `trips`/핀 구조, TourAPI 프록시 12개, `note` 필드, 공유마당)를 최대한 재사용**하는 쪽으로 좁혔다.

## 2. 가져올 것 — 세 분석의 교집합

|---|---|---|
| "담기 → 최적화 → 공유" 3단계 카피가 랜딩에서 명확 | 여로담 랜딩은 다일차·시간표를 강조하지만 중간 단계("일정 만들기")가 상대적으로 덜 부각됨 | 랜딩 3단계를 "핀업 → **일정 만들기(시간표)** → 공유"로 명시하고, 가운데 단계 CTA를 버튼으로 크게 |
| 순서 고정이 시각적으로 분명(배지·잠금 아이콘) | `note` 필드는 있지만 "필수 핀"과 "시간 고정"의 시각적 구분이 약함(캔버스 비교에서 지적된 약점과 일치) | 필수 핀에 잠금 배지 아이콘 추가 — 신규 스키마 없이 기존 우선순위 필드 위에 UI만 |
| 원터치 최적화가 하단 고정 CTA로 항상 보임 | `RouteOptionsPanel.tsx`에 최적화 기능은 있으나 진입 동선이 검색/핀업 대비 눈에 덜 띔 | 최적화 버튼을 데스크톱 하단바/모바일 독에 상시 고정 노출 |
| 실시간 공동편집 | 없음(공유마당의 "가져오기"만 존재) | **지금 만들지 않는다.** 세 분석 모두 이 기능의 무게를 다르게 매기지만("핵심 약속" vs "따라갈지 결정 필요"), 실시간 동시편집은 충돌 해결·권한·활동로그가 딸린 별도 프로젝트다. §4에서 후순위로 명시 |

## 3. 하지 말아야 할 것 — 세 분석의 교집합

세 분석의 "복사하지 말 것" 항목이 사실상 겹친다.

1. **시간표를 버리고 순서만 남기지 않는다** (Wayby 비교의 핵심 경고) — 여로담의 정체성은 "몇 시에 어디"이지 "무슨 순서로"가 아니다. 최적화 기능을 강화하더라도 시간표 뷰를 축소하는 방향으로 가면 안 된다.
2. **결제·재고·정산 인프라를 직접 만들지 않는다** (마이리얼트립 비교) — 예약 링크를 동선에 "배치"하는 것과, 예약을 "처리"하는 것은 완전히 다른 사업이다. §2.2의 제안은 전자에서 멈춘다.
3. **앱스토어 네이티브 앱 설치를 진입 흐름의 기본값으로 바꾸지 않는다** (Wayby 비교) — 지금 강점은 설치 없는 웹 접근이며, 방한 여행자에게는 이게 오히려 더 유리하다.
4. **경쟁사(KTG 포함) 크롤링 금지, 공식 API·제보만** — 이미 이전 검토에서도 확인된 원칙이며 이번 세 분석 어디에도 이를 뒤집을 근거가 없다.
5. **홈을 광고/특가 그리드로 바꾸지 않는다** (마이리얼트립 비교) — 랜딩 카피("담으면 길이 된다")와 정면으로 충돌한다.

## 4. 내 판단 — 실행 우선순위

기존 「통합 개선 개발계획」 검토에서 지적한 것처럼, 일정 엔진 재설계 같은 큰 항목과 UI 표시 개선 같은 작은 항목을 같은 해상도로 로드맵에 놓으면 우선순위가 왜곡된다. 여기서는 **얼마나 기존 코드를 재사용하는지**를 기준으로 3단계로 나눴다.

### Tier 1 — 신규 스키마 없이, 2~3주 내 (기존 필드·컴포넌트 재사용)

| # | 항목 | 근거 | 비고 |
|---|---|---|---|
| T1-01 | 랜딩 3단계 카피 재정렬(핀업→일정 만들기→공유), 가운데 단계 CTA 강조 | Wayby | 카피/레이아웃 변경 |
| T1-02 | 필수 핀에 잠금 배지 아이콘 추가 | Wayby | 기존 우선순위 필드에 UI만 추가 |
| T1-03 | 최적화 버튼 상시 고정 노출(하단바/독) | Wayby | 기존 `RouteOptionsPanel` 진입 동선 개선 |
| T1-04 | `note` 필드 URL 자동 감지 → "예약 링크 열기" 버튼 렌더링 | 마이리얼트립 | 신규 스키마 불필요 |
| T1-05 | `/info` 페이지에 "최근 확인: N일 전" 노출 | KTG | 이미 있는 `fetched_at` 컬럼 재사용 |
| T1-06 | 시나리오 카탈로그 AI 서술에 "이 장소를 넣은 이유" 한 줄 필드 추가 | KTG | 프롬프트/파싱만 확장, 엔진 불변 |

### Tier 2 — 작은 신규 스키마 1~2개, 4~6주

| # | 항목 | 근거 | 비고 |
|---|---|---|---|
| T2-01 | 정보 오류신고(`content_reports`: 장소ID·사유·상태) + 관리자 검수 큐 | KTG | 스키마 1개, 관리자 페이지 1개 |
| T2-02 | 검색·필터에 "예정 방문시각에 영업함" 옵션(현재 "지금 열림"류 필터가 있다면 그 위에 시각 파라미터 추가) | 「통합 개선 개발계획」§4.4에서도 지적된 항목이나 저비용으로 먼저 | TourAPI 영업시간 필드 재사용 |
| T2-03 | 시나리오 카탈로그를 공유마당에서도 발견 가능하게 연결(현재 `SharePlazaPanel.tsx`는 카탈로그를 참조하지 않음 — 확인됨) | 마이리얼트립("목적지로 행동 묶기") + KTG("테마 컬렉션") | 기존 두 기능을 잇는 것, 신규 데이터 없음 |
| T2-04 | Trust Card 컴포넌트화 — 이미 있는 필드(영업시간·반려동반·무장애·주소·출처확인일)를 하나의 카드로 통합 표시 | KTG | 표시 통합, 데이터 소스 그대로 |

### Tier 3 — 신중 검토, 근거 확인 후 착수

| # | 항목 | 이유 |
|---|---|---|
| T3-01 | 실시간 공동편집 | 세 분석 모두 무게를 다르게 매길 만큼 이견이 있는 영역. 지금 공유마당(비동기 복제)으로도 "같이 짜기"의 상당 부분은 우회 가능 — 유료 사용자 요청이 실제로 쌓이는지 먼저 관찰 |
| T3-02 | 예약 제휴 딥링크(가격 연동 없이 링크만) | T1-04로 사용자 스스로 링크를 붙이는 저비용 버전부터 먼저 검증한 뒤, 실제 클릭 데이터가 쌓이면 공식 제휴로 확장 검토 |
| T3-03 | 일정 엔진 고도화(VRPTW 등) | 「통합 개선 개발계획」검토보고서에서 이미 지적: 별도 스파이크로 분리해 최소 케이스부터 실측 필요, 이 개선계획의 범위 밖 |

## 5. 결론

세 서비스를 한 문장씩으로 겹쳐 보면 여로담의 자리가 더 뚜렷해진다.

> Wayby가 "오늘을 같이 짧게", 마이리얼트립이 "무엇을 살지", KoreaTravel Guru가 "어디가 갈 만한지"를 답한다면, 여로담은 **"그래서 그 장소들을 며칠 동안 몇 시에, 실제로 움직일 수 있게"**를 답한다.

이번 개선계획의 요지는 이 자리를 지키기 위해 **새 엔진이나 새 테이블 여러 개가 필요한 게 아니라, 지금 있는 `note` 필드·캐시 컬럼·시나리오 서술·공유마당을 서로 더 잘 잇는 것만으로 Tier 1~2 범위 내(길어도 6주)에서 세 경쟁자의 강점 상당수를 저비용으로 흡수할 수 있다**는 것이다. 엔진 재설계(T3-03)나 실시간 협업(T3-01) 같은 무거운 항목은 이 계획에서 의도적으로 제외했으며, 착수 전 별도 검증이 필요하다.
