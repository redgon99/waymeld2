# 「동선짜기 인터페이스 한국/해외 이중화」계획

> **[폐기됨 — 2026-08-26]** 아래 계획은 채택하지 않기로 결정했다. 사유: 기존 포지셔닝(`positioning-copy.md`, `monetization-strategy.md`)이 "해외"를 "전세계 여행지"가 아니라 "한국여행을 계획하는 외국인"으로 전제하고 있었고, 8/24 검토보고서에서 "전세계 확장"이 이미 범위 폭주 리스크로 명시 지적됐으며, 해외 트랙은 TourAPI 기반 모트가 사라져 Google Places를 얇게 감싼 도구가 될 뿐이고, 비용 통제가 클라이언트 단뿐인 상태에서 트래픽만 키우는 리스크가 있다는 판단에 따른 것. 한국 집중을 유지한다. 문서는 향후 재검토 시 참고용으로 남겨둔다.

## 0. 전제와 스코프 결정 (먼저 정해야 실행이 꼬이지 않는다)

검토보고서에서 이미 확인한 사실을 그대로 전제로 깐다:

- **엔진은 이미 있다.** 좌표 기반 프로바이더 분기(`mapProvider.ts`), 구글 통합검색(`searchPlacesUnifiedWithGoogle`), 구글 상세조회(`fetchGooglePlaceDetail`), 구글 지도 렌더링(`GoogleMapView.tsx`)이 실제로 동작하는 것을 라이브 테스트로 확인했다(검토보고서 §6). 이번 계획은 **"새로 만들기"가 아니라 "이미 있는 엔진 앞에 트랙 분기 UX를 세우는 것"**이다.
- **지금 구조의 근본 결함은 "지역 판정이 사후적"이라는 것이다.** 새 여행은 항상 서울 좌표로 시작하고(`makeEmptyTrip` / `DEFAULT_MAP_CENTER`), 프로바이더 선택은 브라우저 전역 `localStorage`에 저장되어 좌표 판정보다 우선한다. 이 두 가지가 "한국/해외"라는 **사용자 의도를 여행 시작 시점에 붙잡아두지 못하게** 만든다. 이번 이중화 계획의 핵심은 이 의도를 **Trip 생성 시점에 데이터로 고정**하는 것이다.
- **"전세계 모든 나라"를 목표로 하면 비용 구조 결정이 스코프에 포함되어야 한다.** 검토보고서 §3에서 확인했듯 Google Places는 검색 1,000건당 $32~35, 상세조회(리뷰·사진 포함)는 $40이고 무료 한도는 월 1,000~5,000건 수준이다. 한국 국내용 틈새 서비스일 때는 감당 가능한 리스크였지만, "전세계 사람이 전세계 여행을 계획"하는 규모를 목표로 하면 이 단가가 서비스 존속을 좌우하는 변수가 된다. 따라서 이 계획은 Tier 3에 **저비용 검색 + Google 상세조회 온디맨드 하이브리드**(지난 대화에서 검토한 Mapbox/OSM 대안)로의 전환을 명시적으로 포함한다. 이걸 나중에 급하게 갈아엎는 것보다 처음부터 "검색 프로바이더는 교체 가능해야 한다"는 전제로 설계하는 편이 싸게 먹힌다.
- **중국은 별도 문제로 분리한다.** 구글 지도/Places는 중국 본토에서 차단되어 있어 이 계획의 "해외 트랙"에 넣을 수 없다(§5 결정 필요 사항 참고). 이번 계획의 "해외"는 **구글 지도가 실제로 동작하는 국가**로 한정하고, 중국은 스코프 밖에 명시적으로 둔다.

## 1. 설계 원칙

1. **트랙은 추론하지 않고 선택받는다.** 지금처럼 지도 중심좌표를 보고 사후에 한국/해외를 추측하는 대신, 여행 생성 시점에 사용자가 목적지를 검색하거나 "국내/해외"를 선택해 트랙을 확정한다. 좌표 기반 판정(`isKoreaRegion`)은 폐기하지 않고 **트랙이 없는 레거시 데이터의 폴백**으로만 남긴다.
2. **트랙은 Trip에 귀속된다, 브라우저에 귀속되지 않는다.** 지금의 `mapProviderChoice`(브라우저 전역 localStorage)는 한 사용자가 국내 여행과 해외 여행을 같이 굴릴 때 서로 꼬인다. 트랙 값은 Trip 레코드 자체의 필드로 저장한다.
3. **한국 부가서비스는 "설정돼 있으면 켠다"가 아니라 "한국 트랙이면 켠다"로 바꾼다.** 지금 TourAPI·축제 검색은 `isTourApiConfigured()`(키 존재 여부)만 보고 실행되는데, 이러면 해외 트랙에서도 의미 없는 API 호출이 나갈 수 있다. 게이트 조건에 `track === 'korea'`를 추가한다.
4. **새 프로바이더를 추가해도 UI가 안 흔들리게 한다.** `Place` 타입으로의 정규화(`normalizeGooglePlace` 패턴)가 이미 있으므로, Tier 3에서 검색 프로바이더를 더 추가해도 이 정규화 레이어만 확장하면 되도록 유지한다.

## 2. 데이터 모델 변경

`src/lib/trips.ts`의 `Trip` 인터페이스에 목적지 필드를 추가한다. 기존 `region?: string`(현재 사실상 미사용 — Plaza 표시용으로만 존재)과 역할이 겹치지 않도록 별도 필드로 신설한다.

```ts
export type TripTrack = 'korea' | 'overseas';

export interface TripDestination {
  track: TripTrack;
  /** ISO 3166-1 alpha-2, 예: 'KR', 'FR', 'JP' */
  countryCode?: string;
  /** 사용자에게 보여줄 표기, 예: "도쿄, 일본" */
  label: string;
  center: { lat: number; lng: number };
}

export interface Trip {
  // ...기존 필드 유지...
  destination?: TripDestination;
}
```

- `destination`을 옵셔널로 두는 이유는 기존 저장된 Trip(수백 건일 수 있는 로컬/Supabase 데이터)과의 하위호환 때문이다. `destination`이 없는 레거시 Trip은 지금처럼 `isKoreaRegion(mapCenter)` 좌표 추론으로 폴백한다.
- `computeTripCenter`(`tripGeo.ts`)는 그대로 두되, **새 Trip 생성 시에는 이 함수 대신 `destination.center`를 최우선으로 쓴다.** 핀이 하나도 없는 상태에서도 지도가 목적지에서 시작해야 하기 때문이다.
- Supabase `trips` 테이블은 `payload`(JSON) 컬럼에 저장되는 구조이므로(`rowToTrip`의 `payload` 처리 참고) 스키마 마이그레이션 없이 `payload.destination`만 추가하면 된다 — DB 컬럼 추가 불필요.

## 3. 여행 생성 플로우 재설계

현재 `handleNewTrip`은 확인 대화상자 하나만 띄우고 바로 `makeEmptyTrip()`(서울 좌표 고정)을 만든다. 여기에 "여행지 선택" 단계를 끼워 넣는다.

**신규 플로우:**
1. "새 여행" 클릭 → 목적지 검색 입력 (도시/국가명, 예: "도쿄", "파리", "부산")
2. 검색어를 지오코딩(국내는 기존 카카오 주소검색, 해외는 `reverseGeocodeWithGoogle`의 역방향이 아니라 정방향 지오코딩 — Google `Geocoder.geocode({ address })`를 신규로 추가) → 후보 좌표 목록 표시
3. 사용자가 후보 선택 → `countryCode`가 `'KR'`이면 `track: 'korea'`, 아니면 `track: 'overseas'`로 확정
4. `destination` 필드를 채운 `Trip`을 생성, `mapCenter`를 `destination.center`로 즉시 세팅

목적지를 모르거나 건너뛰고 싶은 사용자를 위해 **"국내 여행으로 시작" / "해외 여행으로 시작(목적지는 나중에)"** 단순 토글도 폴백으로 남긴다 — 이 경우 "해외"는 임시로 `DEFAULT_MAP_CENTER`가 아닌 **직전 해외 여행의 마지막 좌표 또는 세계지도 줌아웃 뷰**로 시작해, 최소한 "한국 지도가 뜨는데 해외 트랙"이라는 모순은 피한다.

## 4. 프로바이더/트랙 결정 로직 개편

`resolveMapProvider`를 다음과 같이 우선순위 재정렬한다(현재는 `choice`(브라우저 전역)가 좌표보다 먼저 이기는 구조 — 검토보고서 §2 원인 B):

```
1. trip.destination이 있으면 → destination.track이 곧 provider (korea→kakao, overseas→google)
2. destination이 없는 레거시 Trip이면 → 기존 로직 그대로 (좌표 추론, VITE_MAP_PROVIDER_FORCE, 브라우저 저장값 순)
3. 사용자가 지도 위에서 수동으로 프로바이더를 강제 전환하면(현재 MapProviderPicker) → 그 세션에 한해 override, 단 Trip 저장 시 destination.track은 바꾸지 않음(실수로 트랙이 영구히 바뀌는 것을 방지)
```

이렇게 하면 브라우저 전역 `localStorage` 값은 "레거시 Trip 폴백용 기본값" 정도로 역할이 축소되고, 실질적인 진실의 원천은 각 Trip의 `destination.track`이 된다.

## 6. 단계별 실행계획

### Tier 1 — 구조적 기반 (원인 A·B 해소, 최우선)
- [ ] `Trip.destination` 필드 추가 + `normalizeTrip`에 하위호환 처리(없으면 `undefined` 유지)
- [ ] 여행지 선택 진입 UI(§3) — 목적지 검색 지오코딩(국내: 카카오, 해외: Google Geocoder 신규 연동)
- [ ] `makeEmptyTrip()` → `makeTrip(destination)`으로 교체, `mapCenter` 초기값을 `destination.center`로
- [ ] `resolveMapProvider` 우선순위 재정렬(§4)
- [ ] 한국 부가서비스 게이팅 조건 변경(§5 표)
- 목표: 이 티어만 끝내도 "해외 목적지를 고르면 처음부터 구글 지도로, 아무 조작 없이 시작된다"가 성립한다.

### Tier 2 — 해외 트랙 완성도
- [ ] 검토보고서 §6 라이브 테스트 시나리오(도쿄·파리 검색/상세)를 정식 QA 체크리스트로 편입, 주요 도시 5곳 정도로 확대 검증
- [ ] 카카오↔구글 카테고리 매핑(`mapKakaoCategoryToGoogleType`, 현재 8종) 세분화 — 실사용 카테고리 필터 기준으로 보강
- [ ] 해외 트랙 UI 문구·통화·거리단위 로케일 재점검(9개 로케일은 이미 있음, 표시 포맷만 확인)
- [ ] 서버 측 사용량 집계 최소선 도입(검토보고서 §4 권고 3) — 최소한 일일 총 호출수를 Supabase에 기록해 클라이언트 우회를 완전히 무방비로 두지 않기

### Tier 3 — 글로벌 스케일 대비 (비용 구조 전환, 선택적이지만 "전세계 목표"라면 사실상 필수)
- [ ] 해외 트랙의 "검색/목록"을 저비용 프로바이더(Mapbox Search Box 또는 OSM 기반)로 전환, **"장바구니에 저장한 장소"에 한해서만** Google Place Details 온디맨드 호출 — 지난 대화에서 정리한 하이브리드 구조
- [ ] `searchPlacesUnifiedWithGoogle`의 레거시 `PlacesService` 의존을 신규 Place API(`searchByText`/`searchNearby`)로 이관(검토보고서 §4 권고 6) — 상세조회는 이미 이원화되어 있으므로 검색도 동일 패턴으로 맞춤
- [ ] Free/Plus/Team 티어별 해외 검색 정책 확정 후 반영(§7 결정 필요 사항과 연동)

## 7. 결정이 필요한 사항 (사용자 판단)

- **Tier 3(하이브리드 전환)을 처음부터 넣고 갈지, Tier 1~2로 먼저 출시하고 사용량을 보며 결정할지.** "전세계 스케일" 목표를 진지하게 잡을수록 먼저 넣는 편이 안전하지만, 1인 개발 체제에서는 검증 범위가 늘어난다.
- **중국을 로드맵에 언제 넣을지, 아예 뺄지.** 구글 기반 해외 트랙과는 완전히 다른 API 체계(Amap/Baidu)가 필요해 별도 프로젝트급이다.
- **한국 부가서비스(TourAPI 등)를 해외 트랙에서 완전히 숨길지, 아니면 "이 정보는 한국에서만 제공됩니다" 안내로 대체할지.** UX 톤 결정이 필요하다.
- **Free 티어의 해외 검색 허용 범위** — 검토보고서 §5에서 이미 제기된 사항으로, 이번 계획의 Tier 2/3 우선순위에 직접 영향을 준다.
