# 산악사고 신고자 구조 전 안전관리 PWA 구축계획

## 1. 시스템의 기본 개념

시스템의 목표는 다음과 같이 잡는 것이 좋습니다.

**“119 신고 이후 구조대가 신고자에게 도착하기 전까지 신고자의 위치·신체상태·주변환경·기상·통신상태를 지속적으로 수집·분석하여 위험상황의 변화를 상황실과 출동대가 공유하는 시스템”**

전체 흐름은 다음과 같습니다.

```text
산악사고 신고
      ↓
신고자에게 안전관리 링크 전송
      ↓
PWA 접속
      ↓
위치정보 제공 동의
      ↓
GPS 최초 위치 확보
      ↓
┌─────────────────────────┐
│ 신고자 상태 수집         │
│ GPS / 신체 / 환경 / 통신 │
└─────────────────────────┘
      ↓
공공정보 자동 결합
      ↓
기상 + 산악기상 + 지형 + 등산로
      ↓
위험도 분석
      ↓
상황실 안전관리 대시보드
      ↓
신고자 ↔ 상황실 지속 Check-in
      ↓
위험변화 자동 알림
      ↓
구조대 위치 공유 / 현장 도착
```

핵심은 **“위치를 한 번 받는 앱”이 아니라 “사고 종료 시까지 신고자 상태를 하나의 Incident로 관리하는 것”​**입니다.

# 2. 수집해야 할 정보

## 2-1. 신고자 위치정보

PWA에서 가장 먼저 확보해야 하는 데이터입니다.

웹의 Geolocation API는 HTTPS 환경에서 사용자의 동의를 받아 현재 위치와 위치 변화를 가져올 수 있으며 `getCurrentPosition()`과 `watchPosition()`을 사용할 수 있습니다.

수집 데이터는 다음처럼 구성합니다.

| 데이터 | 중요도 | 비고 |
|---|---:|---|
| 위도·경도 | ★★★★★ | 핵심 |
| GPS 정확도 | ★★★★★ | 10m/50m/500m 구분 |
| 위치 수집시간 | ★★★★★ | 오래된 좌표 방지 |
| 고도 | ★★★★☆ | 지원 기기에서 활용 |
| 이동방향 | ★★★☆☆ | 이동 중인 신고자 |
| 이동속도 | ★★★☆☆ | 이동 여부 판단 |
| 최근 위치 변화 | ★★★★★ | 추락·이동·표류 등 판단 보조 |
| 위치수집 실패 횟수 | ★★★★☆ | 통신/GPS 문제 |

특히 지도상에는 단순한 점 하나보다

```text
현재 신고위치
● 37.xxxxx / 127.xxxxx

GPS 정확도 : ±13m
고도 : 약 742m
최종 갱신 : 18초 전

최근 10분 이동거리 : 23m
```

처럼 표시하는 것이 좋습니다.

# 3. 신고자의 신체·정신 상태 수집

이 부분은 센서보다 **짧은 Check-in 질문**이 훨씬 현실적입니다.

예를 들어 최초 신고 시에는 다음 항목을 받습니다.

| 구분 | 확인 내용 |
|---|---|
| 의식 | 대화 가능 / 반응 저하 |
| 호흡 | 정상 / 불편 |
| 움직임 | 가능 / 어려움 |
| 부상 | 있음 / 없음 |
| 통증 | 변화 없음 / 악화 |
| 체온 관련 | 추움·떨림·젖음 등 |
| 피로 | 정상 / 심함 |
| 심리상태 | 안정 / 불안 / 혼란 |
| 동행자 | 인원 및 상태 |

질문은 길게 만들면 안 됩니다.

예를 들어 구조가 진행 중일 때는 신고자 화면에 크게

```text
현재 상태를 알려주세요.

[ 괜찮아요 ]

[ 조금 나빠졌어요 ]

[ 많이 힘들어요 ]
```

정도로 먼저 보여주고, 이상 응답이 들어왔을 때 추가 질문을 보여주는 방식이 좋습니다.

의료적 위험 판단은 AI가 독자적으로 진단하도록 만들기보다는 **기관의 구급·구조 SOP에서 승인한 질문과 위험 신호를 규칙 기반으로 적용하고, 최종 판단은 상황요원에게 제공하는 의사결정지원 방식​**으로 만드는 것이 적절합니다.

# 4. 주변 상황 수집

신고자가 직접 입력하는 정보와 공공데이터를 결합합니다.

### 신고자가 입력

```text
비가 오나요?
○ 아니오
○ 약하게
○ 많이

몸이나 옷이 젖었나요?
○ 아니오
○ 일부
○ 많이 젖음

현재 위치
○ 등산로
○ 숲속
○ 암벽/절벽 주변
○ 계곡
○ 정확히 모르겠음

비바람을 피할 장소가 있나요?
○ 있음
○ 없음
```

선택적으로 사진 1장을 전송하게 할 수도 있습니다.

사진을 이용하면 이후 AI가

- 눈 적설 여부
- 숲/암벽/계곡
- 등산로 여부
- 야간 여부

같은 환경정보를 **보조적으로 분류**할 수도 있습니다.

# 5. 휴대전화와 통신 상태

여기가 PWA 설계에서 매우 중요합니다.

### PWA에서 가능한 것

배터리 API를 지원하는 브라우저에서는 잔량과 충전 여부를 확인할 수 있지만 Battery Status API는 현재도 일부 주요 브라우저에서 지원하지 않는 **Limited availability** 기능입니다.

따라서 다음처럼 설계합니다.

```text
Battery API 지원

배터리 37%
충전 안 함
      ↓
자동 수집


Battery API 미지원

현재 휴대전화 배터리는?

[ 80~100% ]
[ 50~80% ]
[ 20~50% ]
[ 20% 미만 ]
```

즉 **자동 + 신고자 입력 fallback**을 같이 둡니다.

---

## 6. 통신상태는 Heartbeat가 핵심

휴대전화의 실제 LTE/5G 안테나 감도를 PWA에서 정확하게 가져오는 것은 어렵습니다.

Network Information API도 일부 브라우저에서는 지원되지 않습니다.

그래서 실제 운영에서는 다음을 측정하는 것이 훨씬 신뢰성이 높습니다.

```text
신고자 PWA
     │
     │ 20~30초마다
     │ heartbeat
     ▼
서버

응답시간
패킷 실패
마지막 통신시간
연속 실패횟수
```

예:

```text
통신상태

🟢 정상

마지막 연결 8초 전
응답시간 143ms
최근 10회 성공 10/10
```

상태가 악화되면

```text
🟡 불안정

최근 5회 중 3회 실패
마지막 위치 2분 18초 전
배터리 약 21%
```

통신이 끊기면

```text
🔴 통신두절

마지막 연결 : 7분 전
마지막 GPS : 37.xxxxx / 127.xxxxx
배터리 : 마지막 확인 18%
```

처럼 구조대에게 전달합니다.

# 7. 중요한 PWA 한계

여기서 중요한 설계 판단이 있습니다.

PWA는 화면이 열려 있을 때 `watchPosition()`을 이용한 위치 추적에는 적합합니다. 그러나 모바일 브라우저는 백그라운드 페이지의 타이머를 제한하며, Service Worker와 Background Sync 역시 장시간 지속 실행용으로 설계된 기능은 아닙니다.

따라서

> **PWA만으로 1시간 이상 백그라운드에서 GPS·배터리·통신상태를 100% 지속 수집한다고 가정하면 안 됩니다.**

이를 고려하여 시스템은 2단계로 구축하는 것을 권합니다.

### 1단계

**PWA 중심**

- GPS 위치
- 신고자 Check-in
- 사진
- Heartbeat
- Web Push
- 배터리 지원 기기 자동수집
- 날씨/지형 자동수집

### 2단계

**Android 네이티브 보조 모듈**

- 백그라운드 GPS
- 안정적인 배터리 수집
- 충전상태
- 네트워크 변화
- 앱 백그라운드 동작

으로 확장합니다.

# 8. 신고자와 계속 연결하는 방법

Web Push를 적극 활용할 수 있습니다.

Push API는 웹앱이 현재 화면에 열려 있지 않아도 서버에서 Push를 받을 수 있도록 지원하며 Service Worker와 결합해 동작합니다.

예를 들어 5분 후:

```text
119 구조대가 이동 중입니다.

현재 상태는 어떠세요?

[ 괜찮아요 ]
[ 상태가 나빠졌어요 ]
```

10분 후:

```text
현재 위치를 다시 확인합니다.

[ 위치 보내기 ]
```

상황실에서 직접 보낼 수도 있습니다.

```text
구조대가 약 1.2km 거리까지 접근했습니다.
휴대전화 배터리를 아껴주세요.

[ 확인 ]
```

# 9. 연동할 공공정보 API

## ① 기상청 단기예보 조회서비스 ★★★★★

가장 먼저 연결해야 합니다.

현재 초단기실황·초단기예보·단기예보를 제공하며 전국을 약 5km × 5km 격자로 세분화하여 지역별 날씨를 제공합니다.

신고자의 GPS를 기상청 격자로 변환하여 자동 조회합니다.

활용 데이터:

```text
현재기온
강수량
습도
풍속
풍향
강수형태
향후 기온
향후 강수
```

예:

```text
현재 신고자 주변

기온     4.3℃
습도     86%
풍속     6.2m/s
강수     1mm/h
3시간 후 2℃
```

# 10. 기상청 기상특보 API ★★★★★

강풍·호우·대설·한파·폭염 등 기상특보를 사고지역에 자동 연결합니다.

기상청 기상특보 서비스는 현재 시·군 단위와 해역을 대상으로 주의보·경보 및 예비특보 등의 정보를 제공합니다.

상황판에서는

```text
⚠ 기상 위험

강풍주의보
18:00 발효

예상기온 하락
강수 지속 예상
```

처럼 표시합니다.

---

# 11. 산림청 국립산림과학원 산악기상정보 ★★★★★

이 시스템에서는 일반 기상청 자료와 함께 반드시 검토할 가치가 있습니다.

산악기상정보는 산악지역의 지형적·기후 특성을 반영한 관측정보이며 풍향, 강수량, 지면온도, 습도, 기압 등의 항목을 제공합니다.

즉

```text
기상청
   +
산악기상관측소
```

자료를 같이 보여주는 것이 좋습니다.

---

# 12. 기상청 AWS 관측정보 ★★★★☆

공공기관 시스템이라면 추가로 검토할 가치가 큽니다.

기상청 방재 AWS는 전국 500여 개 지점에서 기온·강수·습도·기압·풍향·풍속 등을 관측하며, 해당 API는 공공기관 대상 심의승인 방식으로 제공됩니다.

산악구조 시스템이라는 활용 목적이 명확하기 때문에 운영 단계에서 연계 검토 가치가 큽니다.

---

# 13. VWorld 레저정보도 ★★★★★

신고자 위치와 **등산로의 관계를 계산하는 데 매우 중요**합니다.

국토교통부 레저정보도는 전국 등산로, 등산로시설, 둘레길 등 공간정보를 WMS/WFS 형태로 제공합니다.

따라서 시스템이 자동으로

```text
신고자 위치
      ↓
가장 가까운 등산로 검색
      ↓
등산로까지 거리 72m
```

같이 판단할 수 있습니다.

이 기능은 구조대 입장에서 매우 유용합니다.

---

# 14. 국토지리정보원 DEM ★★★★★

GPS만으로는 신고자가

- 계곡에 있는지
- 능선에 있는지
- 급경사에 있는지

정확하게 알기 어렵습니다.

국토지리정보원의 DEM은 지표면의 표고를 수치화한 데이터로 제공되고 있으며 방재·공간분석 등에 활용할 수 있습니다.

DEM을 미리 서버 GIS DB에 넣어두면

```text
GPS
37.xxxx
127.xxxx

      ↓

고도     783m
경사도   높음
사면방향 북동
```

등을 계산할 수 있습니다.

실시간 API 호출보다는 DEM을 미리 PostGIS 등에 적재해 사용하는 방식을 추천합니다.

# 15. 국립공원 다목적 위치표지판 ★★★★☆

국립공원 지역에서는 상당히 유용합니다.

국립공원공단은 위치표지판의 고유번호, 고도, 위도·경도 등의 공간데이터를 공개하고 있습니다.

따라서 신고자가 위치표지판을 모르더라도

```text
현재 GPS
       ↓
반경 500m 표지판 검색
       ↓
가장 가까운 위치표지판
03-07
거리 183m
```

처럼 상황실에서 확인할 수 있습니다.

# 16. 생활안전지도 산행안전정보 ★★★☆☆

보조 레이어로 검토할 수 있습니다.

다만 생활안전지도 API는 2025년 11월 전면 개편되어 API 인증키와 호출 URL 체계가 변경되었으므로 신규 서비스에서는 반드시 현재 OpenAPI 인터페이스를 다시 확인해 연결해야 합니다.

따라서 이것은 2차 연계 대상으로 두는 것이 좋습니다.

# 17. 일몰시간 정보 ★★★★☆

산악구조에서는 상당히 중요한 변수입니다.

한국천문연구원의 출몰시각 정보 API에서는 지역 또는 위치 기준으로 일출·일몰과 시민박명 등의 정보를 제공합니다.

상황판에서는 단순히

```text
현재 17:23

일몰 18:12
일몰까지 49분
```

처럼 보여주면 됩니다.

구조대 ETA가 70분이면

```text
⚠ 구조대 예상 도착 전에 일몰 예상
```

이라는 중요 정보가 됩니다.

대화 가능
보행 어려움
추위를 느낌

# 19. 위험도는 4개 영역으로 분리

| 위험영역 | 판단 |
|---|---|
| 👤 신고자 위험 | 상태변화·부상·의식·움직임 |
| 🌧 환경 위험 | 기온·비·눈·풍속·일몰 |

| 📱 통신 위험 | 배터리·heartbeat·GPS |

```text

🔴 긴급
```

으로 표시합니다.

처음부터 머신러닝을 적용하기보다는 **현장 구조대·구급대 SOP를 이용한 Rule Engine → 사고데이터 축적 → 통계분석/AI 모델** 순서가 훨씬 적절합니다.

# 25. 통신두절 대비가 필수

산에서는 통신두절 자체가 정상적으로 발생할 수 있기 때문에 PWA에 **Offline First** 구조가 필요합니다.

```text
통신 정상
   ↓
서버 즉시 전송


통신 끊김
   ↓
IndexedDB 저장

GPS
상태입력
시간

   ↓

통신 복구
   ↓
미전송 데이터 자동 전송
```

그리고 상황실은

> “현재 상태를 모른다”

와

> “상태가 정상이다”

를 절대 같은 의미로 처리하면 안 됩니다.

예를 들어

```text
🟢 정상

🟡 마지막 확인 3분 전

🟠 마지막 확인 7분 전

🔴 마지막 확인 15분 전
```

처럼 **정보 신선도 자체를 위험 요소**로 관리합니다.

# 26. 실제 신고 절차

실제 운용은 다음 10단계로 설계하는 것이 좋습니다.

1. 119 산악사고 신고 접수
2. 상황요원이 사고관리번호 생성
3. 신고자 휴대전화로 1회성 URL 문자 전송
4. 신고자가 URL 접속
5. 위치·상태 공유 동의
6. 최초 GPS + 신고자 상태 수집
7. 서버가 기상·산악기상·지형·등산로·일몰 자동 조회
8. 상황실에 신고자 안전관리 카드 생성
9. 구조 중 GPS·Heartbeat·Check-in 반복
10. 구조대 접촉 후 사고관리 세션 종료

로그인을 시키지 않는 것이 중요합니다.

예:

```text
https://rescue.example.kr/i/Ax78Pq91
```

처럼 **사고별 일회성 Token**으로 접속시키는 방식이 적합합니다.

# 30. 가장 중요한 설계 포인트

이 시스템에서 가장 중요한 것은 **신고자의 위치를 추적하는 것 자체가 아닙니다.**

핵심 데이터는

```text
신고자 상태
     +
위치 변화
     +
환경 변화
     +
통신 상태
     +
구조대 ETA
```

입니다.

예를 들어

```text
신고자 상태 : 조금 악화
기온 : 7℃ → 3℃
강수 : 시작
배터리 : 42% → 19%
일몰 : 28분 후
구조대 ETA : 47분
```

라는 정보가 동시에 들어오면 단순 GPS 시스템에서는 알 수 없었던 **“구조대 도착 전 위험이 커지고 있다”​**는 사실을 상황실이 즉시 인지할 수 있습니다.

따라서 최종적으로는 이 시스템을 단순 **「산악사고 위치추적 앱」**이 아니라

> **「산악사고 신고자 구조 전 안전관리·위험예측 시스템」**

으로 설계하는 것이 가장 적절합니다.

특히 초기 개발에서는 **PWA + Supabase/PostgreSQL(PostGIS) + 기상청 + VWorld + 산악기상 + Web Push** 조합이 구현 난이도와 효과 면에서 가장 좋은 출발점입니다. 이후 현장 검증을 거쳐 Android 네이티브 보조 기능을 추가하면 실제 소방 구조업무에 적용 가능한 수준까지 발전시킬 수 있습니다.
